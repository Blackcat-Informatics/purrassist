## False positives and adjudicated seeds (with evidence)

- **(a) Three `unreachable!` contradicting "Nothing here panics".** False positive. In non-test code at e97a973, 534f862 and e4850a8, the count of `unreachable!|panic!|.unwrap()|.expect(` in bridge/parse/model/write is `0 0 0 0` (`git show <c>:… | sed '/#[cfg(test)]/,$d' | grep -c`). The T2 recheck removed them before the first commit. The remaining slice indexing is invariant-guarded:
  - `parse.rs:400,470` (the value is non-empty by `parse.rs:301`);
  - `parse.rs:552` (`comma_parts` drops empty parts);
  - `parse.rs:684` (`at > start`);
  - `model.rs:297` (`index > 0`).

  `bridge.rs:27-33` turns a tokenize failure into `compile_error!`. The claim at `bridge.rs:11` holds.
- **(b) Version skew between derive and core.** The skew itself is inherent: a proc-macro has no link-time edge to the crate its output names. Model knowledge, not verified here: serde and thiserror force lockstep with exact `=` pins (serde also uses a never-active `cfg(any())` target dependency). Here, `check-release.py:126-128` (`^` only) and `check_derive_closure` (no normal or target dependencies) rule those out. Within 0.1.x only additive changes are possible, so skew yields a compile error, never silent misbehavior. The remaining gap is documentation: **G5**.
- **(c) `Members`/derived `from_node` allocation not charged to a Governor.** Out of scope; not a #8-class regression. `FromNode::from_node(&Node)` (PR #5, `from_node.rs:163-169`) has no governor by design, and every existing impl (String clone, `Vec` collect) allocates ungoverned. It converts a tree that already exists and whose size was bounded by governed recovery or parsing. The derived conversion is O(n log k) time with O(k) `seen` bits per object (k static), plus clones into `extra`: linear in the input. The #8 class concerned uncharged quadratic work inside recovery. The FN1 oracle (`derive_support.rs` tests: 64 names, ≤384 comparisons) guards the single pass. Optional MAXIMAL-PERFORMANCE note, not a gap: `seen: vec![false; k]` (`derive_support.rs:547`) could be a `u64` bitset for k ≤ 64.
